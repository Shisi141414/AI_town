## 出行与车辆规则

| 项目 | 当前规则 |
|---|---|
| 步行 | 室外 3 格/tick，每格额外消耗 0.18 饱食度 |
| 骑行 | 室外 6 格/tick，每格额外消耗 0.25 饱食度 |
| 汽车 | 道路最高 12 格/tick，每格消耗 0.15 金钱；驾车不扣饱食度 |
| 室内 | 一律步行，保持 3 格/tick |
| 共用汽车 | 开局全镇仅 1 辆；一名居民使用时，其他居民不能同时驾驶 |
| 私家车 | 每位居民可花 1000 金钱买 1 辆；只有本人能驾驶，其他室友可以搭乘 |
| 车辆位置 | 停在室外道路上；需靠近取车，不会从远处传送到司机身边 |
| 乘客 | 司机之外最多 3 位；司机须在车位，乘客须在两格范围内 |
| 下车 | 可主动下车；司机离开道路、改成步行/骑行或回家时，乘客自动下车 |
| 余额不足 | 无法购车；不足下一格油费时改为步行，不产生负余额 |

驾车、搭乘期间跳过被动饱食消耗；其他生命、精力、心情规则保留。车外步行和骑行仍有基础生活消耗。骑行的**每格**饱食消耗略高于步行，但每 tick 能走更远；这两个系数可在 `engine/player.py` 调整。

模型会获得车辆位置、归属、占用情况、速度、费用和载人规则。普通行动可附加 `travel_mode`，并支持 `buy_car`、`ride`、`stay_in_car`、`leave_car`。乘客每隔 6 tick 可以重新决定是否继续搭乘；没有 API 时继续使用规则降级。侧栏提供对应的观察和人工干预入口。

## 可以学习和复用的实现方式

### 图像坐标与逻辑坐标分开

寻路仍使用 26×26 地块。室内墙占用的格子保持不变，只把墙画在格子中央，宽度从原来整格缩为约 6/16 格。这能改变观感，同时保留已有门洞和通路。家具目前属于视觉层，不会增加新的碰撞障碍。

`web/pixel-scene.js` 按 16 像素一格绘制基础素材，再放大到室内 32px/格、室外 28px/格。静态场景按地图内容缓存，更新居民时直接复用；中文标签在最终分辨率下绘制，以保证可读性。`web/app.js` 负责交互，CSS 分为基础样式和像素主题，后续改美术无需修改模拟规则。

### 用时间预算统一不同交通速度

把一 tick 看作 1 单位时间。速度为 `v` 时，每走一格花费 `1/v`，逐格扣减，预算不足便停止。例如汽车在纯道路上最多走 `12×(1/12)=1` tick；从道路进入建筑后，该格按步行的 `1/3` 计时。这能避免跨越道路边缘时仍按汽车速度移动。

汽车寻路用 Dijkstra，以逐格旅行时间为边权；步行和骑行仍可用 BFS。司机先走到实际停车点，再驶向目的地，车不会随着人物的步行穿过绿地和房间。

### 把车辆作为共享资源

“选择开车”不等于凭空拥有汽车。`Simulation.vehicles` 保存车辆 ID、归属、司机和位置，居民只持有引用。取得共用车时检查占用关系，购车时检查余额和所有权；HTTP 接口与模型行动调用同一套引擎方法，避免出现两套扣款或搭乘规则。

## 三级记忆管理与低频事件（2026-10-28）

原实现只有120条单层记忆，溢出直接丢弃。现改为一级原始记录、二级精简经历、三级永久深层档案。活动/出行/社交日志按参与居民写入一级，聊天每一句同时写给双方，长记录分段入库；对话结束时继续保留总结。整理门槛同时考虑条数和字数，保留较新的缓冲记录。

| 转移 | 触发门槛 | 处理范围 | 模型提名 | 从提名中抽取 | 全池随机补充 |
|---|---|---|---|---|---|
| 一级→二级 | 48条或10000字 | 最旧最多40条，暂留最新8条 | 10条 | 随机8条，权重0.8 | 2条，权重0.2 |
| 二级→三级 | 24条或5000字 | 最旧最多20条，暂留最新4条 | 5条 | 随机4条，权重0.8 | 1条，权重0.2 |

这里的“全池”包括本次处理范围内所有记录，抽样时排除已经保留的记录，保证不重复；模型提名但没有在第一次抽中的记录也能进入第二次抽取。模型的作用是先提出完整候选名单，然后抽取80%，并非只让模型决定80%的名额。模型主动部分会精简到80字以内；随机部分保留原文并合并空白。模型选择不足或失败时以重要度补足名单，单条来源标明模型、兜底或随机。通过候选ID校验，模型不能凭空新增一条不存在的来源；摘要仍是生成内容，事实精度取决于模型，需要时可在查看器检查。

每位居民使用本地 SQLite 档案，添加即提交；提升写入与源记录删除位于同一事务，取消、写入失败时原记录仍在。只对一级、二级执行淘汰与精简，三级没有遗忘操作；默认居民档案按稳定槽位跨重启、重置恢复。手动居民档案仍留存在磁盘，但原有手动入住名单不随重启恢复。金钱、车辆、疾病等完整世界状态尚不持久化。档案目录忽略提交，不能把“永久”理解成能抵抗手动删文件或磁盘损坏，可自行备份该目录。

**保存与上下文是两件事**：长期保存的三级记忆不会全部加载进提示。每次决策最多8条、2400字；对话最多4条、1200字。每层均获得检索机会，结合关键词、重要度、近期程度和选择权重排序，三级不随时间降低近期分。深层档案从数据库分页及关键词读取，每次最多读取有限候选。压缩请求同样只处理有限候选，不携带整段历史会话。

## 心情机制改版（2026-10-28）

心情结算改为逐 tick 的"基础消耗 + 关系调制"模型，全部集中在 `Player.passive_drain`（每 tick 十分钟调用一次），常量与公式放在 `engine/activities.py` 顶部。基础消耗为每 tick 心情 -1，即不做任何事时约 16.6 小时耗尽。同区域（沿用相遇判定 `world.same_place`：同场景同设施区，路上为两格内偶遇）每有一位好感度超过 60 的室友，每 tick 心情 +2 起步，增益随好感线性上升、斜率每点 0.2，好感 80 时为 +6，满值 100 为 +10；好感 30 至 60 之间不产生影响；好感度低于 30 的同区域室友每 tick 扣 2 起步，减损随好感下降线性加重、斜率每点 0.1，好感为 0 时扣 5。公式为 `relationship_mood_per_tick`：高于 60 时 `2+(aff-60)*0.2`，低于 30 时 `-(2+(30-aff)*0.1)`，好感按 0~100 截断。关系影响是单向的：只看本人对室友的好感，因此迁就对方与厌恶对方可以同时成立。

患病（`illness_severity` 非 0）每 tick 心情 -4，不随严重程度加重。精力低于 20 时每 tick 额外扣除 (20-精力)/10 点心情，即精力归零时叠加 -2，与基础消耗合计 -3。心情低于 20 连续 18 tick（游戏内 3 小时）后开始每 tick 扣 0.5 生命并播报一次，计数在心情回到阈值以上时清零；计数器 `low_mood_ticks` 随检查点全量打包持久化，读档后连续低落不会清零。与装饰加成的叠加关系：装饰度加成仍在活动结算内按 `(房间装饰+公共装饰)/200` 上限 100 生效，二者独立。

数值平衡上，一名好感 80 的室友 (+6) 足以对冲基础消耗与一名患病 (-1-4+6=+1)，而两名好感 0 的室友会把每 tick 净变化压到 -1-5-5=-11，约 7.6 小时从满心情跌到零并开始伤血，鼓励玩家修复关系或搬离。增益斜率 (0.2) 大于减损斜率 (0.1)，善意回报快于恶意惩罚，符合社交正反馈的设计意图。

新增 `tests/test_mood.py` 共 12 项离线检查：公式锚点（61→+2.2、80→+6、29→-2.1、0→-5、中性带与越界截断）、被动结算集成（基础 -1、好感 80 同区域净 +5 且单向、好感 0 净 -6、跨场景增益失效、患病净 -5、低精力按结算后精力计算、连续低落延迟 18 tick 后每 tick 0.5 伤血、恢复清零）。全套 151 项离线检查通过。本改动只涉及引擎结算，前端无需调整，重启服务即生效。
